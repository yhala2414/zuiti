# 话到嘴边：产品问题与演进

## 文档职责

本文维护已经确认的产品问题、处理方向、阶段依赖和进入条件，供需求、规划、跨模块和架构工作使用。它不替代：

- `docs/product-prd.md` 的当前产品合同；
- `docs/architecture.md` 的当前实现边界；
- `docs/verification-guide.md` 的验证要求；
- `AGENTS.md` 的当前阶段和实施权限；
- 飞书中的实时排期、负责人和临时清单。

本文中的阶段、长期方向和设计事项不构成当前实施授权。执行前必须从 `AGENTS.md` 确认当前激活阶段和允许范围。

## 稳定推进原则

- **当前主线：**测试复现与核心修复 → AI 质量基线 → 产品流程确认 → UI/UX 实现 → 架构边界设计 → 最小 Monorepo → 独立生成 API → 数据持久化。
- **并行关系：**Bug 修复、产品需求讨论和必要工程基建可以并行；大范围 UI 实现等待产品流程确认，架构迁移等待核心合同和测试基线稳定。
- **确定方向：**Monorepo 和独立后端已确认为后续必经路线；进入条件满足并完成对应阶段批准前禁止实施。迁移分阶段进行，不与 UI、业务流程或数据库重写混做。
- **贯穿约束：**AI 质量是产品核心，数据隐私是全程门槛；用户可见结果遵守 `docs/product-prd.md` 的产品合同，本文不重复定义。
- **按证据推进：**先复现和记录，再修复和回归。一次审计、截图或源码匹配不能替代可重复的行为证据。
- **克制扩展：**Agent、RAG、长期记忆、账号和第二端必须由对应需求与评测触发，不作为架构装饰。

优先级：P0 阻断当前产品合同、核心体验或证据可信度；P1 是产品完善和上线前建设；P2 在对应方向启动时处理。仅在必要时标记“待验证”“条件进入”或“暂不建设”等状态。

## 当前问题与任务

### 核心流程与状态

#### B-01 · 沟通对象没有进入生成上下文 `P0`

前端要求选择 `target`，但请求校验仍允许缺失，生成上下文、Prompt 和 fallback 也未使用它。“对谁说”是核心产品参数，当前实现不能保证领导、同事等对象产生有意义的表达差异。

处理：将 target 纳入必填公共合同、模型标签、上下文、Prompt 和 fallback；用对象敏感案例验证输出差异。

验收：前后端合同一致，不同对象在保持原意的前提下稳定影响措辞、边界和正式程度。

#### B-02 · 历史记录不能原样恢复 `P0`

历史页只恢复输入并进入结果页，已保存结果不会直接展示，而会重新请求模型，产生等待、费用和结果漂移。

处理：定义可恢复的历史快照；“查看”展示保存结果，另设明确的“基于当前模型重新生成”。

验收：历史结果可离线原样打开，重新生成只能由用户主动触发。

#### B-03 · 再润色与返回链路可能丢失状态 `P0`

结果页部分操作使用整页导航；需统一定义“再润色”“重新生成”“再调整语气”和编辑后生成的行为，并验证浏览器返回与状态保留。

#### B-04 · 对比按钮没有结果路径 `P0`

“查看原话→优化版变化点”没有处理逻辑。完成产品定义后实现；在此之前删除或明确标记未开放，不保留假动作。

#### B-05 · 偏好能力只有展示，没有读写闭环 `P1`

先确定哪些偏好真实影响生成，再建设输入、存储和读取；未实现前不得表现为可用功能。

#### B-06 · 生成逻辑重复且存在竞态风险 `P0`

Tone 与 Results 各自协调生成请求。统一 preview/final 调度，支持取消、去重、过期结果保护和可追踪 operation，防止重复费用和旧结果覆盖。

### AI 质量与安全

#### AI-01 · 缺少可重复的 AI 质量基线 `P0`

当前有 Prompt、few-shot、schema 和 fallback，但没有固定案例、评分规则和质量门槛；“API 调通”不能证明产品有效。

处理：建立覆盖场景、对象、风格和风险的案例集，评价可发送性、原意保留、边界、风格区分、安全和延迟。Prompt、模型、fallback 或生成合同变化必须回归。

#### AI-02 · 生成版本、质量、延迟和成本不可追踪 `P1`

记录 run ID、模型/Prompt/策略版本、source、延迟、token/cost 和错误类别；默认不记录用户原文。

#### AI-03 · 内容安全仍是 MVP 最低防线 `P1`

用红队案例驱动输入/输出规则、拒绝和安全改写；上线前补齐审计与必要的人工复核策略。

#### AI-04 · Agent、RAG 与长期记忆暂不建设 `P2 · 待证据`

只有 AI-01 证明单次结构化生成无法解决明确任务时，才分别立项；每项必须有独立收益基线、隐私边界和回退方案。

### 测试与工程

#### E-01 · 现有测试不能证明关键旅程可用 `P0`

现有测试多数读取源码并匹配字符串，只有少量测试执行真实函数。保留有价值的静态合同检查，增加领域单测、Route Handler 集成测试和少量生产构建 Playwright 旅程。

核心旅程至少覆盖：正常生成、安全拒绝、fallback、错误/超时、重复操作、状态缺失、历史恢复和结果操作，并检查 `375 × 750`。

#### E-02 · 生产依赖存在已知高危漏洞 `P0`

最近审计发现 Next.js、axios 及传递依赖存在 6 个 high severity 问题。按官方升级说明定向更新，禁止用 `npm audit fix --force` 代替兼容性验证。

#### E-03 · 缺少最小交付门禁 `P1`

架构迁移前建立包含 lint、test、build、核心 E2E 和 dependency audit 的最小 CI；独立后端出现后再增加部署、迁移和回滚门禁。

### 产品与 UI/UX

#### UX-01 · 当前三步流程缺少用户证据 `P1`

通过任务访谈和可用性测试比较现流程与“更短输入、生成后调节”等方案，不凭审美直接重做。

#### UX-02 · 移动端信息架构仍是 MVP 形态 `P1`

重点处理首屏价值、输入密度、结果可读性、状态反馈、触控和 `375 × 750` 布局；先确认流程和设计，再大范围实现。

#### UX-03 · 持续动画影响可访问性和测试稳定 `P1`

限制动画时长，支持 `prefers-reduced-motion`，避免交互控件持续改变几何位置。

UI 阶段需形成稳定的品牌 tokens、页面状态和通用组件规则，但不默认更换 `antd-mobile + CSS Modules`；只有现有方案经实际验证阻碍设计或可访问性时才评估替代。

### 数据与隐私

#### D-01 · 反馈与行为数据没有持久化闭环 `P1`

feedback/track 目前只写控制台。核心旅程稳定后先完成最小匿名事件、反馈及数据治理设计，明确 schema、幂等、保留期与权限；持久化实现等待最小 Monorepo 与独立生成 API 完成。

#### D-02 · 日志和宽松载荷可能暴露敏感表达 `P0`

logger 会记录原话片段，previous context 与 track payload 边界宽松。立即停止默认记录正文并收紧 schema；数据库建设前完成数据分类、同意、加密、访问、保留和删除设计。

默认原则：只保存必要运行元数据和聚合信号；正文只有在用途明确、用户同意且具备完整治理能力时才能保存。

#### D-03 · 账号与云同步后置 `P2`

Phase 5 建立匿名数据闭环后，再根据跨端连续性需求建设可升级账号；匿名用户仍能完成核心任务。

### 生产能力

#### P-01 · 公共 AI 端点缺少成本和滥用保护

- **当前 P0：**处理明显的无限请求、重复请求和无边界费用风险。
- **后续 P1：**随独立 API 建设输入大小、匿名配额、风险限制、并发/成本上限、可取消请求、熔断和告警。

#### P-02 · 缺少可观测性 `P1`

定义生成成功率、fallback 比例、拒绝率、p50/p95 延迟、成本和核心转化；独立 API 阶段建立健康检查、trace、指标和告警。

#### P-03 · Web 上线能力不完整

- **P1：**上线前完成 CSP、正式错误状态和性能监测。
- **P2 / 条件性：**manifest、service worker 等 PWA 能力等待复访与安装需求成立。

### 架构演进

#### A-01 · 先明确边界，再迁仓 `P1`

当前领域类型、浏览器状态和应用模块仍有穿透。架构设计必须先划分 Web、domain、contracts、AI/server 的职责、I/O、数据所有权和依赖方向。

#### A-02 · 最小 Monorepo 是确定路线 `P1 · 条件进入`

进入条件：核心 P0、测试与 AI 质量基线稳定，目标架构获批。第一阶段只迁：

```text
apps/web
packages/domain
packages/contracts
```

不预建 API、管理端、小程序、worker 或 UI 包；不同时重写 UI、状态、数据库或生成行为。

验收：Web URL、API、行为和部署方式不变；共享包不依赖 React、Next、Zustand 或浏览器 API；任务图和完整验证通过。

#### A-03 · Monorepo 后拆独立生成 API `P1 · 条件进入`

先迁生成纵向链路，Web `/api/generate` 保留兼容代理；后续再迁反馈、事件、持久化和必要异步任务。框架、API 版本、部署和数据库访问方式在架构设计阶段决定，本文不预选。

验收：Web 不感知服务地址；直连 API 与 Web 代理合同一致；服务可独立部署、观测和回滚，并具备超时、取消、限流、配置校验及模型/fallback 集成测试。

#### C-01 · 演进方向与当前授权必须分开 `P1`

本文确认长期方向，但不授权实施。当前实施权限只在 `AGENTS.md` 维护；进入新阶段时先更新该入口，再将真实变化同步到 PRD、架构和验证规则的所属权威面。

## 阶段路线

### Phase 0 · 核心稳定与证据基线

处理 B-01～B-06、AI-01、E-01～E-02，以及 D-02、P-01 中的当前高风险部分。产品需求讨论可以并行，但不迁架构、不全面重做 UI。

完成：核心流程、结果操作、历史恢复及主要失败状态有可重复证据；对象真实影响生成；AI 变更可回归；没有已知 high/critical 生产依赖问题；正文不再默认进入日志。

### Phase 1 · 产品流程与 UI/UX

研究核心用户任务、最短输入、生成后决策和复访价值，确定流程、状态、移动原型和设计系统基础；处理 UX-01～UX-03 与 B-05。

完成：用户场景、预期行为、成功指标和可用性证据明确，大范围页面实现有获批方案。

### Phase 2 · 架构、合同与数据设计

处理 A-01 和 C-01；定义 Monorepo 边界、独立生成 API、公共合同、匿名身份、数据分类、部署、兼容和回滚，不迁代码。

完成：职责、I/O、依赖、失败模式、验证和回滚决策完整，相关正式文档同步到获批边界。

### Phase 3 · 最小 Monorepo

执行 A-02，只做结构迁移并保持行为不变。完成后 Web 仍可独立部署。

### Phase 4 · 独立生成 API

执行 A-03，并完成 P-01～P-02 的服务端基线。生成链路稳定后再接反馈、事件和持久化。

### Phase 5 · 数据闭环与生产完善

依次完成 AI 版本与运行指标、反馈/事件存储、生成元数据和成本、隐私治理、告警/SLO、CI/CD。关系型持久化默认优先评估 PostgreSQL，但 schema、ORM 和部署位置须单独设计。

### Phase 6 · 账号与第二端

基于真实数据选择管理端、微信小程序、PWA 或原生方向，再单独立项。第二端必须消费公共合同，不能复制 Web 业务逻辑；账号服务跨端连续性，不强迫首次登录。

## 维护与证据生命周期

问题状态按实际需要标记，不强制每项套用完整模板：

- **已确认：**有当前证据支持，尚未关闭；
- **验证中：**现象、影响或方案仍需复现；
- **已解决：**实现和对应回归证据均已完成；
- **阶段后置：**方向有效，但进入条件或实施授权尚未满足；
- **历史证据：**只描述注明日期和版本的过去状态，不代表当前事实。

维护规则：

1. 修复或决策改变问题状态时，更新对应条目和验证依据；没有回归证据不得标记“已解决”。
2. 已解决问题从当前问题区移出；只有仍能解释现行合同或决策时，才保留一行历史摘要。
3. “最近验证”必须注明日期、分支或版本，并始终视为时间点证据；文档编辑本身不刷新产品验证结论。
4. 阶段进入条件改变时更新本文；激活阶段或实施权限改变时先更新 `AGENTS.md`，再同步实际受影响的产品、架构和验证事实。
5. 飞书继续维护实时排期、负责人和临时清单，不复制到本文。
